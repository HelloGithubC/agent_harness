# 规则：轻量按需验证与反过度测试准则 (Minimal-Verification & Anti-Test-Bloat)

## 核心原则：按需验证，严禁过度工程化 (Verify Minimally, No Test Bloat)

测试的目的是高效辅助确认改动有效，而不是为了表演流程规范。严禁在未经授权的情况下过度编写测试、陷入复杂的测试环境搭建、滥用全量回归测试，或将测试痕迹污染生产代码。

### 1. 编写测试的权限控制 (Test Creation Boundary)
- **非明确要求不新建测试套件**：
  - 除非用户明确要求（如“补充单测”、“编写测试用例”），Agent **严禁主动新建测试文件、搭建新测试框架或引入测试库**。
  - 对于日常 Bug 修复与小功能迭代，优先采用现有机制或最轻量的验证方式。

### 2. 生产端代码纯洁性 (Production Code Cleanliness)
- **严禁测试污染生产代码**：
  - 严禁在生产业务代码中保留仅用于测试过程的临时探针、断言、严格校验逻辑、测试专用分支（如 `if (isTest) ...`）或临时打桩逻辑。
  - 交付的生产代码必须纯粹聚焦于实际业务需求，保持精炼简洁，不得为迎合测试或验证流程而在业务代码中引入无意义的防护与包袱。

### 3. 执行测试的局部化原则 (Targeted Execution Only)
- **严禁擅自全量测试**：
  - 禁止在修改局部代码后盲目执行全量测试（如无脑运行 `pytest`、`npm test` 跑完全仓）。
  - 仅允许运行**直接相关**的单一测试文件或单一具体用例（例如 `pytest tests/test_foo.py::test_bar`）。
- **执行时间与成本可控**：如果针对性测试需要耗费较长时间或有复杂前置准备，先向用户确认是否需要执行。

### 4. 严禁陷入“测试死循环” (No Meta-Testing Traps)
- **环境卡点立即停**：
  - 若执行测试时报错是由于“缺少测试依赖、未启动外部数据库/服务、Docker 环境未配置”，**严禁擅自尝试安装全局依赖或折腾环境配置**，应立即停止。
- **严禁为了测试而写测试**：
  - 禁止编写为了通过测试而将外部逻辑 100% Mock 掉的“无实意占位测试”。
  - 当测试代码本身报错（而非被测业务报错）且一次修正未果时，立即停止折腾测试，直接向用户说明。
